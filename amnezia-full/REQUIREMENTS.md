# Amnezia Full — требования к проекту

Заготовка требований к системе управления AmneziaWG с сегментацией по организациям, ACL между подсетями и веб-интерфейсом для администрирования.

---

## 1. Назначение

- **Самостоятельный проект** (не форк текущего amnezia-wg-fresh): управление WireGuard/AmneziaWG с фокусом на обход DPI, сегментацию сети по организациям и централизованное управление правилами доступа.
- Целевая аудитория: корпоративный/административный сценарий, несколько организаций (тенантов), изоляция и выборочный доступ между подсетями.
- Стек: **Python (FastAPI)** — бэкенд; фронтенд — веб-панель; фаервол — управляемый из API (nftables или iptables с обёрткой).

---

## 2. Функциональные требования

### 2.1 WireGuard / AmneziaWG

- Один интерфейс `wg0` с поддержкой **нескольких подсетей** (например 10.8.1.0/24, 10.8.2.0/24 — по одной на организацию).
- Генерация конфигов клиентов с параметрами AmneziaWG (I1–I5, Jc, Jmin, Jmax, S1–S4, H1–H4), профили маскировки (QUIC, DNS, SIP и т.д.), уровни обфускации (I0–I5).
- CRUD клиентов с привязкой к организации (подсети).
- Выдача уникального IP из подсети организации при создании клиента.
- Скачивание конфига, QR-код (где уместно по размеру).

### 2.2 Организации (тенанты)

- Сущность **организация**: имя, описание, выделенная подсеть (например 10.8.N.0/24).
- Клиенты принадлежат одной организации.
- В будущем: роли внутри организации, квоты.

### 2.3 Сегментация и ACL

- **По умолчанию:** трафик между подсетями (организациями) **запрещён**.
- **Исключения:** возможность задать разрешения «подсеть A может общаться с подсетью B» (или с конкретным хостом/подсетью).
- Правила должны применяться **динамически** (без перезагрузки всего фаервола где возможно): добавление/удаление правил через API и немедленное применение.
- Конфигурация правил не должна превращаться в «миллион строк»: хранение в БД, генерация минимального набора правил (nftables/iptables) из модели «кто с кем может говорить».

### 2.4 Фаервол

- Использование **nftables** (рекомендуется как современная и удобная для автоматизации подсистема) или iptables с чёткой структурой цепочек.
- Правила, управляемые приложением: отдельные цепочки/таблицы, не смешивать с ручными правилами администратора (где это возможно).
- API для: просмотра текущих правил, добавления/удаления исключений между подсетями, сброса к политике по умолчанию (все межподсетевые запрещены + выбранные разрешения).

### 2.5 Бэкенд (FastAPI)

- REST API для: организации, клиенты, конфиги, QR, правила ACL (фаервол).
- Аутентификация и авторизация (минимум: один админ; в перспективе — роли, возможно мультитенантность по доступу к API).
- Хранение данных: БД (SQLite для старта, с возможностью перехода на PostgreSQL).
- Валидация входных данных (Pydantic), единый формат ошибок.

### 2.6 Фронтенд

- Веб-интерфейс для: просмотра организаций и клиентов, создания/редактирования клиентов, скачивания конфигов, управления правилами доступа между подсетями (исключения из общего запрета).
- Доступ только для авторизованных пользователей.

### 2.7 Деплой и окружение

- Запуск в Docker (или на хосте с доступом к `wg`, `nft`/`iptables`, привилегии NET_ADMIN и т.п.).
- Конфигурация через переменные окружения и/или конфиг-файл.
- Документация по установке и настройке.

---

## 3. Нефункциональные требования

- **Безопасность:** пароли не в открытом виде, секреты в env/секрет-менеджере; валидация и санитизация вводов.
- **Масштабируемость:** архитектура допускает рост числа организаций и клиентов без «конфига на миллион строк»; правила фаервола компактны и генерируются из БД.
- **Поддерживаемость:** код структурирован, разделение слоёв (API, сервисы, репозитории), комментарии и документация по ключевым решениям.

---

## 4. Вне границ (v1)

- Мультипользовательский доступ с разными ролями (кроме одного админа).
- Управление несколькими физическими хостами/нодами.
- One-time links, 2FA, OIDC — по желанию в следующих итерациях.

---

## 5. Связанные документы и решения

- Порядок правил фаервола: **исключения (разрешения) задаются до общего запрета** (или в отдельной цепочке с большим приоритетом), чтобы «разрешить A↔B» работало при общем «запретить всё между подсетями».
- Правила применяются **динамически**: добавление/удаление правил через `nft`/`iptables` без перезапуска сервисов; конфиг фаервола можно перегенерировать и применять по запросу из API.
- Текущий проект (amnezia-wg-fresh) остаётся «лёгкой» версией для одного админа и одной подсети; Amnezia Full — целевая платформа для сценария с организациями и ACL.
