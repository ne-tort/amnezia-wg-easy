# Каскадный (double) VPN: режимы и интеграция с remote-deploy

Документ описывает варианты топологии «клиент → входной узел → выходной узел» в контексте **одного хаба AmneziaWG-Easy на машину** и привязки к текущей модели продукта (SQLite, один интерфейс `awg0`, один `[Peer]` в клиентском конфиге). Не заменяет настройку маршрутизации на ОС — фиксирует **сценарии** и **как отразить намерение** в `remote-deploy` (секция `topology`, вывод при `--dry-run`).

## Ограничения текущего продукта (кратко)

| Аспект | Поведение в репозитории |
|--------|-------------------------|
| Хаб | Один деплой = один `server_config`, один `ListenPort`, интерфейс `awg0` |
| Клиентский конфиг | Один `[Peer]` (сервер), один `Endpoint`; `AllowedIPs` из правил firewall (split-tunnel) |
| Multi-hop в одном `.conf` | Не генерируется панелью; потребовалась бы доработка ядра/клиентов |
| NAT / форвардинг | Включены; `PostUp`/nftables завязаны на подсеть VPN и `WG_DEVICE` |

Подробнее по коду: `src/lib/WireGuard.js`, `src/config.js`, `src/lib/firewall/nftables.js`.

## Сводная таблица режимов

| Фича / сценарий | Плюсы | Минусы | Сложность | Пригодность для AmneziaWG-Easy |
|-----------------|-------|--------|-----------|--------------------------------|
| **A. Два деплоя + ручной site-to-site между шлюзами** — S1 и S2 как два отдельных инстанса (разные `WG_DEFAULT_ADDRESS`); между хостами отдельный WG/OpenVPN и статические маршруты; клиенты только на S1, интернет с IP S2 за счёт маршрутизации S1→S2 | Не ломает модель «один `[Peer]` у клиента»; обфускация на участке клиент↔S1 настраивается штатно (I1–I5); используется уже включённый forwarding/NAT на узлах | Два хаба в эксплуатации; нет единого UI; участок S1↔S2 и DPI там — отдельная ручная настройка второго туннеля | Ручной админ + документация | **Высокая** — без изменений панели, в пределах стека |
| **B. «Всё через S2» (упрощённый MVP)** — один публичный VPN-вход на exit; пользователи подключаются к S2 напрямую | Минимум связности между узлами; один инстанс WG-Easy на пользователя | Не даёт низкой задержки для «своих» на ближнем узле; не соответствует идее p2p на S1 | Документация | **Высокая** как простой сценарий |
| **C. Двойной туннель на клиенте** — два активных VPN (например два профиля / два клиента ОС): первый до S1, второй до S2 | Не требует доработки серверного кода WG-Easy | Двойной MTU, порядок маршрутов, петли; не все клиенты стабильно держат два AWG; split-tunnel нужно вручную согласовать с `AllowedIPs` | Пользователь + поддержка | **Средняя** (продукт не мешает, но не помогает) |
| **D. Второй hop в одном конфиге / несколько `[Peer]`** | Единый UX при наличии поддержки в клиентах | Изменения в генераторе конфигов, БД, возможно клиенты AmneziaWG | Глубокая переработка ядра | **Низкая** на текущем этапе — долгосрочный вариант |
| **E. DPI / двойная инкапсуляция (наблюдения)** | Гибкость: разные профили I1–I5 на разных участках при **двух** туннелях | Задержка ≈ сумма RTT; фрагментация; типичные жалобы на скорость и «не открывается» | Документация + тюнинг MTU | **Совместимо** с A/C: параметры задаются **на каждом** туннеле отдельно |

## DPI, MTU и задержка

- При **двух последовательных туннелях** (вариант C или цепочка WG+WG на сервере) накладывается **двойной оверхед** заголовков; снижение `MTU` (в продукте: `WG_MTU` в `.env`, см. `src/config.js`) часто обязательно для стабильности.
- **Обфускация AmneziaWG** (Jc, junk, H1–H4, I1–I5) настраивается **на сервере/в выгружаемом клиентском конфиге** для **одного** туннеля до данного хаба. Второй участок (отдельный WG между S1 и S2) — **отдельный** интерфейс и **свой** набор параметров вручную.
- **Один** туннель только до S1: один слой AmneziaWG на пути «клиент–вход»; выход в интернет через S2 обеспечивается **маршрутизацией на серверах**, а не вторым `[Peer]` в файле из панели.

## MVP vs полная реализация

| | MVP | Полная реализация в продукте |
|---|-----|------------------------------|
| Цель | Задокументировать цепочки и проверять деплой через `--dry-run` | Встроенные роли entry/relay/exit, выдача конфигов с multi-hop, федерация политик |
| Средства | Два деплоя + ручной site-to-site (A) или один вход на S2 (B); опционально клиентский double VPN (C) | Доработка БД, `WireGuard.js`, клиенты, тесты |
| Dry-run | Секция `topology` в YAML — только **описание** намерения и напоминание шагов | Те же ключи + автоматизация по мере появления API |

## Рекомендуемый путь

1. **Self-hosted без форка ядра панели:** вариант **A** (два инстанса + ручной site-to-site, клиенты на entry) — если цепочку администрирует серверная команда и нужен иностранный exit с **одним** клиентским туннелем AmneziaWG до ближнего узла.
2. **Если второй туннель должен быть на устройстве пользователя:** вариант **C**, с явным предупреждением про MTU и маршруты.
3. **Упрощение без p2p на ближнем узле:** вариант **B**.

Вариант **D** оставить в бэклоге до согласования с клиентскими приложениями AmneziaWG.

## Интеграция с `remote-deploy`: секция `topology`

Секция **описательная**: не меняет генерируемый `.env` и не выполняет SSH-команды для настройки каскада. Нужна для:

- единого места в репозитории, где зафиксированы **роли** узлов (entry/exit) относительно **текущего** деплоя;
- вывода в **`--dry-run`** напоминаний и условных шагов «вручную на entry…».

### Имя режима

- В YAML: поле `topology.mode` (строка, см. enum ниже).
- Опционально в `.env` для совместимости с внешними скриптами: **`DEPLOY_TOPOLOGY`** — не обрабатывается контейнером `amnezia-wg-easy` в текущем коде; только документация и будущие обёртки.

### Допустимые значения `topology.mode` (enum)

| Значение | Смысл |
|----------|--------|
| `manual_site_to_site` | Два (или более) хаба; между шлюзами отдельный туннель/маршруты вручную; клиенты обычно на entry |
| `client_double_tunnel` | Два туннеля на стороне клиента |
| `single_exit_only` | Один узел / прямой выход без каскада (явная пометка «без оптимизации p2p на entry») |
| `unspecified` | Зарезервировано: топология не классифицирована |

### Схема YAML (пример)

```yaml
# Пример: текущий деплой — entry; второй сервер описан для справки.
topology:
  mode: manual_site_to_site
  entry:
    host: "wg-entry.example.com"
    wg_port: 51820
  exit:
    host: "wg-exit.example.net"
    wg_port: 51820
  notes: "Клиенты только на entry; exit — исходящий интернет."
```

- Поля `entry` / `exit` **опциональны**; указывайте их так, чтобы не путать с `env.WG_HOST` текущего запуска: **`env`** описывает **этот** сервер, **`topology`** — роли в **логической** цепочке (второй сервер может быть только в `topology.exit`).

### Что печатается при `--dry-run`

После блока с замаскированным `.env` скрипт выводит секцию **«Cascade / double VPN (informational)»** (если задан `topology`):

- режим `topology.mode`;
- хосты/порты entry/exit (если заданы);
- текст `notes`;
- значения полей, по имени ключей похожих на секреты, маскируются как `(hidden)` при печати;
- дополнительные нумерованные шаги **7+** — напоминания **без выполнения** (например настройка маршрутизации между entry и exit).

Базовые шаги **1–6** по-прежнему описывают только реальный деплой WG-Easy на **текущий** хост (Docker, sync, `deploy.sh`, пароль админа).

### Маскирование секретов

- В **`.env`**: как в `remote-deploy/install.py` — ключи, в верхнем регистре содержащие подстроки `PASSWORD`, `SECRET`, `TOKEN`, `PRIVATE`, `PRESHARED`, выводятся как `(hidden)`.
- В **`topology`**: при выводе рекурсивно маскируются значения, если имя ключа (без учёта регистра) содержит те же подстроки **или** `KEY` (например `preshared_key`, `wg_private_key`).

## Риски

- Два полноценных хаба **на одном хосте** в одном compose-проекте не поддерживаются моделью (фиксированные `awg0`, один порт, один volume БД) — потребовались бы отдельные проекты и переименование интерфейсов.
- Клиентский конфиг из панели **не выражает** server-side multi-hop; документируйте отдельно **серверную** цепочку и **клиентский** путь.
- Жалобы на связь при каскаде чаще всего связаны с **MTU** и порядком маршрутов — имеет смысл явно прописать в `notes` принятые значения и ограничения.
