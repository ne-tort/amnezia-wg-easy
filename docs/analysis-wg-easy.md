# Сравнение с wg-easy и рекомендации

Краткий технический разбор отличий текущего wg-easy (master) от форка amnezia-wg-fresh и что имеет смысл переносить.

## Контекст

- **wg-easy** — актуальный проект (TypeScript, Nuxt 3, Nitro, Drizzle, SQLite, Vue 3).
- **amnezia-wg-fresh** — форк на базе старой ветки wg-easy (Node, h3, Vue 2, JSON-конфиг в файле).
- Форк отстаёт на сотни коммитов; полный перенос на стек wg-easy нецелесообразен. Ниже — принципиальные отличия и то, что можно взять точечно.

---

## Принципиальные отличия (по коммитам и коду)

### 1. Хранение данных

| | wg-easy | amnezia-wg-fresh |
|---|--------|-------------------|
| Конфиг | SQLite (Drizzle), отдельные таблицы: interface, clients, users, hooks, oneTimeLink, userConfig, general | Один JSON-файл (`wg0.json`) |
| Сессия | Своя схема сессий в БД, привязка к пользователю | express-session в памяти (секрет из randomBytes) |

В wg-easy конфиг WireGuard собирается из БД и записывается в `/etc/wireguard/<interface>.conf`. У нас всё состояние — в одном JSON, без миграций и схемы. Для одного админа и одного интерфейса этого достаточно.

### 2. Пользователи и доступ

- **wg-easy:** несколько пользователей (логин/пароль из БД), роли, права на ресурсы (definePermissionEventHandler), 2FA (TOTP), отдельные клиенты на пользователя.
- **Форк:** один пароль из env (`PASSWORD`), один «пользователь», все клиенты общие.

Принципиальное улучшение wg-easy — мультитенантность и разграничение доступа. Для self-hosted панели с одним владельцем не обязательно.

### 3. Setup и первый запуск

- **wg-easy:** пошаговый setup (шаги 1→2→3→4), проверка шагов (defineSetupEventHandler), миграции БД, возможность миграции со старого формата.
- **Форк:** при первом запросе конфига ключи генерируются и пишутся в JSON, отдельного wizard нет.

У нас проще: достаточно задать `WG_HOST` и при необходимости `PASSWORD`.

### 4. Валидация и безопасность API

- **wg-easy:** Zod-схемы на все вводы (логин, создание/обновление клиента, фильтры и т.д.), `readValidatedBody` + `validateZod`, единый формат ошибок (createError с statusCode/statusMessage).
- **Форк:** проверка только `if (!name)` при создании клиента; для `clientId` — явный запрет `__proto__`/`constructor`/`prototype`; тело запроса без схемы.

Принципиальное улучшение — предсказуемая валидация и безопасный парсинг. Имеет смысл перенести точечно: санитизация/ограничение имени клиента (длина, символы), при желании — единый формат ошибок.

### 5. Дополнительные функции wg-easy (по коммитам)

- **One-Time Links** — ссылка на скачивание конфига с ограниченным сроком жизни.
- **Срок действия клиента (expiresAt)** — автоматическое отключение по дате.
- **Поиск/фильтр клиентов** — по имени и адресу (в БД через like).
- **Prometheus/JSON metrics** — метрики за защищённым Bearer-токеном.
- **CIDR для адресов** — расчёт подсетей (cidr-tools), раздельные IPv4/IPv6.
- **Hooks (PreUp/PostUp/PreDown/PostDown)** — кастомные команды из БД на интерфейс.
- **Clean filename при скачивании** — то же правило, что у нас (санитизация имени, лимит 32), в wg-easy вынесено в `cleanClientFilename`.
- **QR:** перебор уровней ECC при переполнении; у нас — фиксированный компактный конфиг без I1.

Часть из этого (фильтр, метрики, one-time links, expiration) завязана на БД и многопользовательность; в форк без смены архитектуры не переносится. Санитизация имени файла у нас уже есть; валидация имени клиента и единый формат ошибок — реалистичные точечные улучшения.

### 6. Фронт и стек

- **wg-easy:** Nuxt 3, Vue 3, TypeScript, отдельные страницы (setup, admin, clients, me), composables, Pinia-подобные stores, отдельные JSON для i18n.
- **Форк:** один HTML + Vue 2, один app.js, сообщения в одном i18n.js.

Полная замена фронта на Nuxt/Vue 3 — принципиальное улучшение по структуре и типизации, но очень объёмная работа; для текущих целей не обязательно.

### Итог по принципиальным отличиям

- **Реально «принципиальные» в wg-easy:** БД вместо файла, мультипользователи и права, setup-wizard, валидация (Zod) и единый формат ошибок, 2FA, one-time links, expiration, метрики, фильтр клиентов.
- **У нас принципиально проще:** один конфиг-файл, один пароль, минимум валидации, фокус на AmneziaWG и DPI-обход.
- Для self-hosted сценария «один админ, одна панель» архитектура форка достаточна. Имеет смысл позаимствовать только: **валидацию/санитизацию имени клиента**, при желании — **единый формат ошибок API** и **Cache-Control для статики**. Всё остальное — либо избыточно, либо тянет за собой смену стека (БД, Nuxt, мультипользовательность).

## QR-коды

- **Ёмкость QR:** максимум при Version 40 и низкой коррекции ошибок (L) — **2953 байта** (режим Byte). Конфиг уже в ASCII; смена на «ANSI» или другую однобайтовую кодировку размера не уменьшает.
- **QR в UI:** используется компактный конфиг (без I1), чтобы QR был читаем камерой. Полный конфиг в QR получался слишком плотным. Подсказка: через QR конфиг менее устойчив к DPI; для полного обхода — Скачать.

## Безопасность и валидация

- В форке уже есть защита от опасных `clientId`: проверка на `__proto__`, `constructor`, `prototype` в маршрутах API — это разумно оставить.
- В wg-easy есть `cleanClientFilename` для имён файлов конфигов (санитизация имени, лимит 32 символа). В форке при скачивании конфига имя файла строится так же (в `Server.js`), дублировать отдельной утилитой не обязательно.
- Обязательный HTTPS, 2FA, one-time links в wg-easy вы не хотите — не переносим.

## Архитектура и стек

- wg-easy: TypeScript, Nuxt/Nitro, БД (Drizzle + SQLite), отдельные репозитории и API по клиентам/интерфейсам.
- Форк: один JSON-файл конфига, классический Express-like API.
- **Рекомендация:** не пытаться портировать архитектуру wg-easy целиком. Для self-hosted панели текущая схема с одним конфигом и простым API достаточна. Перенос на TypeScript/Nuxt имел бы смысл только при желании развивать форк в сторону многопользовательности, 2FA и т.п.

## Что можно при желании позаимствовать (точечно)

1. **Обработка ошибок API** — в wg-easy ошибки возвращаются единообразно (тип, код). Можно ввести простой формат `{ error: string, code?: string }` в ответах ошибок форка.
2. **Заголовки кэширования** — для статики (HTML/JS/CSS) в wg-easy выставляются Cache-Control; можно добавить в раздачу статики форка.
3. **Лимиты на длину имени клиента** — в wg-easy имя обрезается/санитизируется; в форке при создании/редактировании клиента можно добавить проверку длины и запрет недопустимых символов.

## Что не переносим

- Переход на БД (SQLite) — избыточен при текущей модели «один конфиг».
- One-Time Links, срок действия клиентов, 2FA, Prometheus — по вашему запросу не нужны.
- Полная замена фронта на Nuxt/Vue 3 — большой объём работ без явной выгоды для текущих целей.

## Итог

- **QR:** восстановлен в UI с компактным конфигом (без I1); при переполнении бэкенд повторяет генерацию без I1.
- **Технические улучшения:** защита по `clientId` уже есть; при необходимости можно добавить единый формат ошибок API, кэш-заголовки для статики и валидацию/санитизацию имени клиента.
- Крупный рефакторинг по образцу wg-easy не рекомендуется без цели (многопользовательность, 2FA и т.д.).
