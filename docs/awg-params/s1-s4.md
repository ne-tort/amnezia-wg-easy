# S1–S4 — message padding

## Смысл

Псевдослучайный префикс к типам сообщений WireGuard/AmneziaWG:

| Поле | Сообщение | Базовый размер WG |
|------|-----------|-------------------|
| S1 | Initiation | 148 + S1 |
| S2 | Response | 92 + S2 |
| S3 | Cookie reply | 64 + S3 |
| S4 | Transport (data) | variable + S4 |

## Hard limits

- S1 ≤ 1132 (≈1280−148)
- S2 ≤ 1188 (≈1280−92)
- S3 ≤ 1216 (≈1280−64); в практике Architect non-extreme: **1–64**
- **S4 ≤ 32** (жёсткий потолок протокола; каждый байт на каждом data-пакете)

## Критичные коллизии длины

- `S1 + 56 ≠ S2` — иначе Init и Response совпадают по длине
- `S2 + 92 ≠ S3` — иначе Response и Cookie совпадают

Генератор панели соблюдает оба правила с retry.

## Адекватные рамки рандома (панель)

| Поле | Типичный random |
|------|-----------------|
| S1 | 15–150 |
| S2 | 15–150 |
| S3 | 8–64 |
| S4 | 4–32 (для «лёгких» профилей верх ужимаем, напр. 16–24) |

S4 поднимает DPI-стойкость и **постоянно** режет throughput — для DNS-мимикрии держим скромно.

## Влияние

- S1/S2 — маскируют handshake sizes (главное против простых классификаторов).
- S3 — реже на критическом пути.
- S4 — на каждый data-пакет; важнее умеренность.
